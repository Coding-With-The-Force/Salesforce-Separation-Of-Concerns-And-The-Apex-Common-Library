How the site is put together

Markdown goes in. Pages come out.

Everything between those two things is machinery you set up once and then mostly forget. This walks through each piece of it — what feeds what, and where to go when you want to change something.

01The pipeline, end to end

Five stages. You only ever touch the first one.

docs/*.mdx→ docs plugin→ MDX compiler→ theme swizzles→ build/

In plain terms: Docusaurus is told to look in ../docs. It reads the frontmatter at the top of each file to learn the title and the URL, hands the body to the MDX compiler, and the compiler turns your markdown into a React component. Any <Tag /> it meets gets looked up in the component registry. Finally the theme wrapper puts that component inside the site shell — navbar, ruler, rails, footer — and writes the whole thing out as a plain HTML file.

Why this matters

Nothing in stages 2–5 knows anything about the Apex Common Library. They are generic. All the subject matter lives in the seventeen markdown files, which is why you can keep writing prose and never touch React.

Why your h1 isn't in the markdown

Each chapter has hide_title: true in its frontmatter. That tells Docusaurus not to print the title into the article body, so the layout can render it up in the masthead instead — above the standfirst and the meta line. If you paste an # H1 back into a chapter file you'll get two titles.

03One table feeds five things

website/src/data/chapters.ts is the spine of the whole site. It is a plain list of seventeen objects, and five separate parts of the site read from it. Change a chapter's URL there and it changes everywhere at once, including the redirect from the old address.

What each field is for

FieldWhat it does
nChapter number. Drives reading order, the ruler position, and which chapters are "before" this one.

There is no template engine

template: 'pattern' does not switch layouts. Every chapter uses the same layout. The field only prints a word in the meta line and in the homepage index.

What actually makes a "pattern chapter" look different is which components you put in the file. A pattern chapter is one where you wrote a <PatternCard>. That's the whole mechanism. If you add a component to a chapter, update the label to match — nothing will break if you don't, it will just say the wrong word.

The frontmatter contract

Every chapter file starts with the same five lines. Three of them must agree with the chapter table.

docs/10-The-Domain-Layer.mdxfrontmatter
---
title: "The Domain Layer"          # must match chapters.ts
slug: /domain-layer/                # must match chapters.ts
sidebar_position: 10              # must match n
hide_title: true                 # always — the masthead renders the h1
---

Adding one to another chapter

Open the chapter, type the tag, save. There is no registration step and no import. The reason only a few chapters use these today is that pointing them at more chapters means reshaping prose, which is an editing decision rather than a technical one.

05The CSS, in four layers

Four files, loaded in this order. Later files depend on earlier ones, so the order matters.

FileOwns
tokens.cssEvery colour, size and spacing value, for both themes. Also repoints Docusaurus's own variables at them so its built-in bits inherit the palette.
base.cssThe blueprint grid, body type, prose, code blocks, callouts, navbar, footer.
shell.cssThe ruler, the two-column page, the section rail, the masthead, the pager.
components.cssEverything an author can drop into a chapter.

Two of the tokens are worth knowing by name, because they control how wide the content is:

  • --cw-read — how wide prose runs. Currently 104ch.
  • --cw-wide — how wide things with internal structure run: code blocks, the comparison, figures, the pager. Currently 115ch.

Both live in tokens.css and nothing else hardcodes a width, so those two numbers are the only dials for the reading measure.

The one thing that isn't a token

Code blocks stay dark in light mode on purpose. The syntax colours come from src/theme/prismTheme.ts and are tuned for a dark panel — inverting them would mean inventing a second colour scheme that isn't in the brand.

06How it gets published

push to main→ GitHub Actions→ npm ci→ typecheck→ build→ GitHub Pages

Pushing to main is the whole deploy. The workflow in .github/workflows/deploy.yml installs from the committed lockfile, type-checks, builds, and hands the output to GitHub Pages. There is no server anywhere — the result is a folder of HTML files.

Three things that protect you

  • Broken links fail the build. onBrokenLinks: 'throw' means a link to a chapter that doesn't exist stops the deploy instead of shipping a dead link.
  • The lockfile is committed. npm ci rebuilds the exact same dependency tree every time, so a package can't change under you without a commit.
  • The domain is in the repo. website/static/CNAME carries apex-enterprise-patterns.dev, so it survives a settings reset.
The old URLs still work

All seventeen MkDocs addresses redirect to their new homes. Those redirect pages are generated from the legacy field in the chapter table, so they can never drift out of sync with the real URLs.

Working on it locally

terminalbash
cd website
npm install        # once
npm start          # dev server, reloads as you type
npm run build      # the real build — catches broken links
npm run serve      # preview that build exactly as it will ship
One habit worth having

npm start is forgiving; npm run build is not. Run the build before pushing anything structural — it's the same command CI runs, so if it passes locally it will pass there.
